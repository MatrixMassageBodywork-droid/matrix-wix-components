# Owner report and technical appendix

Lead with a brief plain-language conclusion, not a wall of diagnostics. Use the following structure as needed; retain exact evidence in the appendix.

## Owner summary

- Scope: exact URLs/page count and page types; audited count, deferred count and reasons. New page versus existing page.
- What is already working: verified strengths and items requiring no edit.
- What performance says: source-backed findings and material uncertainty, with dates. State unavailable Google reports plainly.
- Highest-priority opportunities: confirmed defects first, then evidence-backed opportunities. No guaranteed ranking claims or arbitrary SEO grades.

## Page performance

| Page | Page type / intent | GSC clicks and impressions | CTR / avg position | Organic landing sessions | Booking clicks | Period comparison and confidence |
|---|---|---|---|---|---|---|

Keep unavailable values as “not available.” Separate source definitions/periods. A zero must be evidenced. Do not present average position as a live local rank. Mark booking clicks as a microconversion, not completed appointments. A source's broader session-level key events are labeled accordingly.

## Approval-ready changes

Plan ID: [stable ID]; revision: [N]; digest: [computed]; prepared: [time/timezone].

| ID | Page / exact field | Current value | Proposed value | Why / evidence | Priority and likely benefit | Scope / risk |
|---|---|---|---|---|---|---|

For long copy or code, point to the exact before-and-after appendix rather than abbreviating the proposed changes beyond reviewability. Label each item required, recommended or optional. Include changes on linking pages separately. Mark already satisfied checks and not-tested items without suggesting unnecessary work.

State exactly what approval will do: save drafts, or save and publish. Present all proposed edits and validated candidate files before asking. Do not bundle new permissions, analytics installations, GBP edits, URL removals or redirect changes into a generic SEO approval.

## Technical appendix

1. Inventory, current architecture and authoritative checkpoint references.
2. Source/date/filter details and aggregate exports; query-to-page map and incoming/outgoing link graph/table.
3. Per-page checklist with pass/fail/not-tested/not-applicable, evidence and confidence.
4. Exact source baseline, before/after patches, proposed schema and copy, dependency map and baseline hashes.
5. Validation performed and results; deterministic live steps, checkpoints, stop conditions and evidence requirements.
6. Approval evidence and selected change IDs, kept with the private project report.

## Completion receipt

| Change IDs / URL | SAVED | VERIFIED | TESTED | PUBLISHED | Evidence / remaining issue |
|---|---|---|---|---|---|

Include actual source commit/release, permanent public URLs, exact saved/live comparisons, tests that could not run, and the performance baseline for later evaluation. Do not imply untested integrations work. Preserve the audit's source-availability distinctions through the final response.
